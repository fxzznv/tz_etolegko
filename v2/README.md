# Adrobot — конструктор и редактор кампаний Keitaro

Веб-приложение для работы с рекламным трекером Keitaro через Admin API v1:

1. **Создание кампании** — по названию, гео-коду страны, ID оффера и
   справочникам домена/группы/источника создаёт в трекере кампанию с двумя
   потоками: первый принимает трафик только из указанной страны и
   редиректит на Google, второй отправляет остальных на выбранный оффер.
2. **Редактор кампании** — загружает потоки кампании из Keitaro и позволяет
   локально добавлять/удалять/возвращать офферы, закреплять доли и
   задавать проценты; изменения уходят в трекер кнопкой **Push**.

Репозиторий: https://github.com/fxzznv/tz_etolegko (проект в каталоге `v2/`).

**Стек:** FastAPI + SQLAlchemy (SQLite по умолчанию) + Alembic, фронт —
ванильный JS, отдаётся самим бэкендом.

## Требования

- Python 3.9+
- ключ Keitaro Admin API v1 (в админке, раздел может называться иначе:
  Maintenance → Users → Key for Admin API, либо Account → API keys)
- для демо-режима без трекера — ничего, ключ не нужен

## Запуск

```bash
cd v2
cp .env.example .env          # заполните KEITARO_URL и KEITARO_API_KEY
# или для демо без трекера: KEITARO_MOCK=1

cd backend
python3 -m venv .venv
source .venv/bin/activate     # Windows: .venv\Scripts\activate
pip install -r requirements.txt

# миграции БД (создают таблицы campaigns и streams)
alembic upgrade head

# тесты логики долей (опционально, нужны dev-зависимости)
pip install -r requirements-dev.txt
python -m pytest tests -q

uvicorn app.main:app --host 127.0.0.1 --port 8000
```

Откройте http://127.0.0.1:8000

При первом запуске таблицы также создаются автоматически
(`Base.metadata.create_all`), но для продакшена используйте Alembic.

## Как это работает

### Создание кампании

`POST /api/campaigns` создаёт в Keitaro кампанию (state=disabled), затем два
потока и включает кампанию:

- поток `regular` с фильтром `country = <код>` → `action_payload:
  https://www.google.com/`, position 1;
- поток `default` со `schema=landings` и одним оффером share=100,
  position 2.

Если Keitaro не подтвердил шаг, недособранная кампания удаляется через
`DELETE /campaigns/{id}` (см. «Откат при сбое»), а в ответе API — ошибка
с alias кампании для ручной проверки.

### Редактор

- `POST /api/campaigns/{id}/fetch` — читает кампанию и её потоки из
  Keitaro, сохраняет в SQLite. Офферы, пропавшие из трекера, попадают в
  локальный архив (`state="removed"`). Отказывается работать при наличии
  неопубликованного черновика.
- `POST /api/streams/{id}/offers/{add|remove|restore|pin|unpin}` — правит
  черновик (`draft`) и пересчитывает доли.
- `POST /api/streams/{id}/push` — сравнивает черновик с текущим состоянием
  в Keitaro; если поток меняли снаружи — 409, иначе `PUT /streams/{id}`
  с новым списком offers.
- `POST /api/streams/{id}/cancel` — откатывает черновик к published.

Локальные поля `pin` и `share` не уходят в Keitaro — в API передаются
только `{offer_id, share, state}`.

### Алгоритм долей

После каждого изменения черновика `redistribute()` в `app/shares.py`
приводит активные офферы к сумме ровно 100%:

- офферы с `pin=True` сохраняют свою долю;
- остаток `100 − Σ(pin)` делится поровну между активными офферами без
  `pin`; остаток от деления раздаётся по одному проценту первым в списке
  (например, офферы `[A, B, C]` → A получает 34, B и C по 33);
- `removed`-офферы в расчёте не участвуют;
- ошибки: сумма pin-долей > 100%, все активные офферы закреплены и их
  сумма ≠ 100%, активных офферов нет — возвращается 422.

Удаление последнего активного оффера блокируется той же проверкой
«нет активных офферов».

Покрыто unit-тестами (`backend/tests/test_shares.py`, pytest):
1 оффер, 3 оффера с остатком, pin + остаток, сумма pin > 100%,
все офферы закреплены, удалённые офферы, формат payload для API.

### Откат при сбое создания кампании

Если создание потоков или включение кампании падает, бэкенд вызывает
`DELETE /admin_api/v1/campaigns/{id}`.

**Документация Keitaro:** DELETE архивирует кампанию — она пропадает из
основного списка и при необходимости восстанавливается через
`POST /campaigns/{id}/restore` (список архивных — `GET /campaigns/deleted`).

**Учебный стенд-эмулятор (KT Emulator), на котором проводился прогон:**
кампания получает `state='deleted'` и становится недоступной через API v1
(`GET /campaigns/{id}` → 404); при этом `GET /campaigns/deleted` отвечает
422, а `POST /campaigns/{id}/restore` — 404, то есть на эмуляторе удаление
фактически безвозвратно через API. Поведение настоящего Keitaro может
отличаться — сверяйте с документацией вашей версии.

Если DELETE не удался (таймаут, ограничения версии) — в ответе
возвращается alias кампании для ручной проверки в трекере.

Alias кампании генерируется заново при каждой попытке — короткий
`token_hex(5)` (10 символов `[0-9a-f]`, допустимый алфавит alias в
Keitaro: `a-z`, `0-9`, `-`, `_`; alias входит в URL кампании, поэтому
длинный uuid не используем). Повторное создание после архивации не
конфликтует: коллизия 10-символьного hex маловероятна, а при отказе API
ошибка возвращается с alias для ручной проверки.

Форматы запросов и ответов Admin API v1 сверены с публичной реализацией
аналогичного инструмента: https://github.com/rs-an/offer-flow-manager;
код приложения написан самостоятельно.

## API (кратко)

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/meta` | режим работы (demo или реальный трекер) |
| GET | `/api/options` | домены, группы, источники из Keitaro |
| GET | `/api/offers?q=` | поиск офферов |
| GET | `/api/campaigns` | локальные кампании |
| GET | `/api/campaigns/{id}` | кампания с потоками |
| POST | `/api/campaigns` | создать кампанию в Keitaro |
| POST | `/api/campaigns/{id}/fetch` | загрузить потоки из Keitaro |
| POST | `/api/streams/{id}/offers/{action}` | правка черновика |
| POST | `/api/streams/{id}/push` | опубликовать черновик |
| POST | `/api/streams/{id}/cancel` | откатить черновик |

## Что проверено, а что нет

**Проверено на учебном стенде-эмуляторе KT Emulator** (Admin API v1,
ключ из админки; тестовые кампании с префиксом `adrobot-test-` после
прогона удалены через DELETE):

- справочники `domains`, `groups?type=campaigns`, `traffic_sources`,
  `offers` — форматы совпали, правок клиента не потребовалось;
- создание кампании: ровно 2 потока в нужном порядке — `regular` с
  фильтром `country=<код>` и редиректом на Google (position 1), `default`
  со `schema=landings` и оффером share=100 (position 2); кампания
  `state=active`, домен/группа/источник выставлены, alias из 10 hex
  принят;
- редактор: fetch, add, pin с процентом, remove, restore, Push —
  `PUT /streams/{id}` подтверждён удалёнными `share` в трекере;
- трекер принимает раскладку 34/33/33 с суммой 100 (3 оффера);
- гонка: внешнее изменение потока → Push отвечает 409, после
  cancel+fetch работа восстановлена;
- откат: при сбое создания второго потока кампания удаляется через
  `DELETE /campaigns/{id}` (проверено end-to-end на стенде).

**Проверено на `KEITARO_MOCK=1`:** тот же цикл без реального трекера.

**Unit-тесты:** `python -m pytest tests -q` → 8 passed
(алгоритм долей: 1 оффер, 3 оффера, pin+остаток, pin>100%, все pin,
removed-офферы, payload).

**Ограничения:**

- поведение редактора сверено по описанию видео из задания,
  предоставленному заказчиком (колонки таблицы, пересчёт долей до Push,
  содержимое Push, отсутствие статистики), а не по самому ролику;
- у удалённых офферов доля выводится как `0%` и в payload для Keitaro не
  входит; в таблице они помечены `[removed]` с кнопкой Bring back;
- `PUT /streams/{id}` не принимает элементы со `state="removed"` —
  payload формируется без них (см. `api_payload`);
- эндпоинты `campaigns/deleted` и `campaigns/{id}/restore` на
  KT Emulator не работают (422/404) — на настоящем Keitaro, судя по
  документации, это архивация с восстановлением; см. «Откат при сбое»;
- статистика кликов/конверсий из отчётов Keitaro не интегрирована —
  редактор оперирует долями и состояниями офферов.
